# 自我對弈訓練：決策和量測

[English](selfplay-training-guidance-2026.md) · [指令速查](cheatsheet.zh-TW.md) · [引擎](native-engine.zh-TW.md)

檢查日期：2026-10-04。**最新模型繼續學，比賽負責選 best。** 存檔修正已在一次短比較中降低開銷，但還沒證明棋力更強，或 batch／並行量已經最佳。

## 訓練政策

目前已實作的政策：

| 選擇 | 目前做法 |
| --- | --- |
| 主要目標 | 棋力優先，不為了 CPU／GPU 使用率犧牲棋力 |
| 自我對弈 actor | 最新 learner；升級失敗不退回舊權重 |
| 恢復訓練 | 完整 `latest.pt` 約每 60 秒在安全點保存，啟動、里程碑、正常停止也會存 |
| 里程碑 | 每完成 1,000 盤匯出固定的模型檔；數字算棋局，不是更新次數 |
| 比賽候選 | 開始新比較時選最新固定里程碑；略過積壓的舊候選，已開始的比較不在中途換模型 |
| Best | `incumbent.json` 選定接受的里程碑，`best.pt` 原子匯出它 |
| 第一個里程碑 | 初始基準，還沒驗證棋力 |
| 升級 | 100 盤／50 組相同開局交換黑白，至少 55 分、全部棋譜驗證、最大回合超時 0.1 秒 |
| Gate 預設上限 | 每完整回合 0.25 秒，包含六子棋兩次落子；雙方模擬上限相同，預設 64 次 |
| 評估排程 | 每四秒實測訓練時間累積一秒評估額度；GPU 工作輪流執行，未完 gate 可以等 |
| 保留方式 | 留下全部編號里程碑；磁碟滿了停止，不刪舊檔 |
| 調參 | 另行決定前，預設仍是 batch 128／並行 64／六個工作執行緒 |
| Replay 容量 | 新 run 每個完成局面存入八個視角，400,000 筆保留 50,000 個原始局面；已有 checkpoint 沿用保存的上限 |

使用者後來調整了 replay 容量和比賽候選的選擇。預設每 1,000 盤保存里程碑，因此自我對弈到 10,450 盤時，下一次比較用 `model-00010000.pt` 對當時接受的 best。若 2,000 盤模型的比較已開始，先把它比完，再跳過 3,000–9,000。最新里程碑已比過，就等下一份，不回頭補比舊候選。全部 checkpoint 檔案仍保留；持續更新的 `latest.pt` 不會改變比賽中的模型。

八視角、400,000 筆的預設是使用者選定的設定，不是實測棋力增益；學習 batch 大小不變。下面的舊量測和試跑都用 20,000 個原始局面，還沒以較大的儲存 buffer 重新量測。

55 分是快速、暫定的退步篩檢，不是棋力提升的統計證明。沒過的模型仍可能產生訓練樣本；保護 best 不會把那些樣本移除，也不代表它們品質更好。

先前的量測授權只涵蓋暫存副本，以及**所有 GPU 測試程序合計最多 300 秒**，包含啟動、載入和暖機；沒有授權持久訓練或長期棋力比賽。

## 研究支持什麼，又沒證明什麼？

KataGo 官方指南允許 gated 和 ungated 兩種接受方式。有 gate 時，自我對弈用最新接受的模型；沒有 gatekeeper 時，每次匯出都能成為 actor。設定說明指出，沒有 gatekeeper 的 run 通常也能運作，而且可能更有效率；早期 gating 則有助於除錯和檢查進步。這表示可以選，不是六子棋的標準答案。

我們用的是混合做法：latest 推動學習，比賽選出對弈 best。單張 GPU 不必等 actor 通過比賽，但還沒證明每小時棋力更好。如果反覆出現明顯退步，再把「用已接受 best 產生資料」當成另一個實驗。

KataGo 也會限制相對於新樣本的學習量，提醒避免過度重複使用資料。它的單機循序流程建議，訓練成熟後可降低每輪和匯出開銷。那些範例設定測試有限，不能直接當成六子棋預設。

2026-10-04 查閱的來源：[官方訓練指南](https://github.com/lightvector/KataGo/blob/master/SelfplayTraining.md)、[設定說明](https://github.com/lightvector/KataGo/blob/master/cpp/configs/training/README.md)和[單機流程](https://github.com/lightvector/KataGo/blob/master/python/selfplay/synchronous_loop.sh)。

## 為什麼先改存檔？

修改前，檢查的 15×15 六子棋 run 暫停在 2,000 盤／10,944 次更新。Best 仍是第一份基準，下一次比賽只完成一盤，當時的 100% 得分看不出棋力。看到的 5% GPU 使用率／約 2,002 MiB VRAM 是暫停時的數字，不能據此認定訓練還有多少餘裕。

該 run 的累計時間：

| 工作 | 秒數 |
| --- | ---: |
| CPU 搜尋 | 177.0 |
| 原生推論 | 127.5 |
| 學習 | 99.0 |
| Checkpoint 和匯出 | 244.0 |

這是累計階段時間，不是使用率百分比。舊程式每輪學習都保存完整 replay，所以比起先做非同步管線，應該先量存檔。

暫存 CPU 副本的 20,000 樣本 checkpoint，在暖機後量得以下中位數：

| 存檔工作 | 秒數 |
| --- | ---: |
| 序列化 | 1.2001 |
| 寫入並確保落盤 | 0.0383 |
| 完整保存 | 1.2383 |

主要時間花在序列化。因此移除的是多餘存檔呼叫，**不是** `fsync`、原子替換、optimizer／replay 狀態、磁碟上限或復原檢查。長學習週期裡的安全點仍可定時保存；下一次間隔從成功保存結束後才開始算，里程碑發布也保留恢復用 checkpoint。

## 那次短 CUDA 比較

新舊存檔頻率從 **358 盤 checkpoint 的相同暫存副本**，依序執行。都是 15×15 六子棋、batch 256、並行 64、六個工作執行緒、36 秒訓練迴圈額度。兩邊都還沒到里程碑比賽。

| 結果 | 舊頻率 | 新頻率 |
| --- | ---: | ---: |
| Session 計時，含最後存檔 | 36.9 s | 37.1 s |
| 新完成棋局 | 92 | 128 |
| 每 session 分鐘棋局數 | 149.6 | 207.0 |
| 新學習更新 | 448 | 672 |
| 完整 checkpoint 次數 | 12 | 2 |
| Checkpoint／匯出時間 | 13.00 s | 2.17 s |

**這一次短比較，每分鐘棋局數約多 38.4%。** 不是長期保證、不是棋力結果，也不是搜尋 kernel 變快。棋局長度和計時戰術會變動；新 run 保留有限 loss、optimizer 狀態和 64 盤可恢復的未完棋局。

另外的暖機後元件測試交替執行大小案例：

| 檢查 | 較小設定 | 較大設定 | 看得出什麼 |
| --- | --- | --- | --- |
| 原生落子 | 64 根節點：中位 0.2009 s | 128 根節點：中位 0.3518 s | 每秒落子約多 14%，不是完整棋局吞吐量 |
| 學習更新 | Batch 128：中位 0.0124 s | Batch 256：中位 0.0203 s | 每秒處理樣本約多 22%，但單次更新更慢 |

更新次數相同時，batch 256 會抽到 batch 128 兩倍的樣本。處理更快不代表學得更好，也不是相同學習量的比較。Allocator 峰值不包含全部 driver／context VRAM。訓練後的模型也通過一次 CUDA 完整回合檢查：合法下兩子，再把控制交回黑棋。

三個 GPU 測試程序合計 **105.498 秒**，含啟動／載入／暖機，低於當次核准的 300 秒。每個程序都有 watchdog。暫存副本已移除，SHA-256 確認原始 `data/` 檔案未變。原始本機紀錄：`.native-cache/training-save-profile.json` 和 `.native-cache/training-tuning-cuda.json`，不進 Git。

## Batch-256 試跑

存檔修正前，獨立的 batch-256 試跑目錄 正常暫停在 **358 盤、1,984 次更新、20,000 replay 局面**。總／策略／價值 loss 都是有限值：3.0435126／2.7973495／0.2461631。計時為搜尋 65.01 秒、推論 40.48 秒、學習 27.94 秒、保存／匯出 43.04 秒，session 181.0 秒；setup 不在 session 計時內。

這能證明 batch-256 設定跑得動，不能證明比相同起點的 batch-128 試跑快，或棋力更好。想自己用 PowerShell 試：

```powershell
$trial = "data/connect6-15x15-b256-" + (Get-Date -Format "yyyyMMdd-HHmmss")
uv run python train.py --preset connect6 --board-size "15*15" --data $trial --device cuda --batch 256 --parallel 64 --workers 6 --hours 0.05
```

要用新目錄：續訓即使傳 `--batch 256`，也會沿用原本 batch。這是三分鐘的**訓練迴圈**額度，不是整個程序上限。一次只跑一個 GPU 試驗；並行量另測，正式改預設前也要算進資料重複使用量的變化。

## 怎麼防止存檔退步再次出現？

測試檢查原因，不把硬體相關的 207 盤／分鐘當成通過門檻：

- 短 CPU run 做幾輪學習，還沒到自動保存或里程碑時，只能有**兩次**完整 checkpoint：啟動和停止。修正版通過；舊程式寫了五次，測試會失敗。
- 慢更新測試檢查定時保存、保存的待更新工作和續訓；計時器在存檔結束後重設，不重複做週期存檔。
- 其他測試保留固定里程碑、完整 latest、只有模型的 best、匯出中斷修復、剛好 55 分的邊界、超時／棋譜檢查、磁碟上限和發布失敗復原。
- CLI 要有實際 loss／里程碑／剩餘時間，不捏造更新前 loss，並保留比賽／錯誤／保存訊息。Chrome 檢查 55% 圖表參考線和穩定版面。

```sh
uv run python -m unittest discover -s tests -p test_connections.py -k short_run_saves -v
uv run python -m unittest discover -s tests -v
uv run --frozen --group browser python tests/ui_smoke.py
```

存檔修正階段通過 74 個 CPU 測試，耗時 29.678 秒，也通過已安裝 Chrome 的 smoke check。後續清理結果另記在[驗證紀錄](migration-validation.zh-TW.md)，不把舊時間當新量測。

重構可能讓未完 gate 的 checksum 不符。只有續訓提示時才用 `--restart-gate`，它會封存舊比較。不要自動重啟或混用結果。Latest／best／里程碑的用途不變，一般 15×15 六子棋訓練和續訓指令見[操作速查](cheatsheet.zh-TW.md)。
